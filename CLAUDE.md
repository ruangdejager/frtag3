# frtag3

Firmware for the Farmranger LoRa tag (STM32WLE5CC, FreeRTOS, STM32CubeIDE).

frtag3 is a fork of `../frtag2` created for new hardware with a slightly different pin
configuration. The code is currently an exact copy of frtag2 apart from the project name
and the firmware version; divergence for the new board starts from here.

## Working rules

- **Never commit until explicitly told to.** Leave changes in the working tree.
- **Never push until explicitly told to.**
- Work happens on `develop`. `master` holds the initial import.
- `frtag3.ioc` is hand-managed — do not edit or regenerate it unless asked.

## Layout

| Path | Contents |
| --- | --- |
| `Core/` | CubeMX-generated startup, IRQ vectors, `FreeRTOSConfig.h`, clock init. Regenerated by CubeMX — do not hand-edit outside the USER CODE guards. |
| `Drivers/` | ST CMSIS + STM32WLxx HAL/LL vendor library. |
| `Middlewares/` | FreeRTOS kernel, SubGHz_Phy middleware (vendor). |
| `SubGHz_Phy/`, `Utilities/` | ST radio phy package and ST utility packages (LPM, trace, timer, misc). |
| `Hal/` | This project's hardware abstraction over ST's HAL. |
| `Platform/` | OS-level services above `Hal/`: heartbeat scheduler, settings engine, RTC/datetime, string helpers. |
| `fr_app/` | The Farmranger application. |
| `build_scripts/` | `create_release_hex_files.ps1`, the CubeIDE post-build packaging and publish step. |

### Layering

```
fr_app/{Tasks,Worker,Device}   product behaviour
        |
Platform/                      generic OS services, no pinout knowledge
        |
Hal/                           board pinout + STM32 peripheral wrappers
        |
Drivers/                       ST HAL/LL
```

`Hal/hal_bsp.h` is the single pin/peripheral assignment header (LED ports, UART instances,
SPI chip selects, ADC channels). `Hal/inc/hal_*.h` wrap ST HAL calls into peripheral-named
macros and absorb board quirks (for example `HAL_SPI_FLASH_vEnsureAwake()` restores a bus
parked by STOP2). Because the pinout is the thing changing for this board, expect new-board
work to concentrate in `Hal/`.

`Platform/` never knows pin numbers. It provides the 1 Hz heartbeat dispatcher
(`PLATFORM_bSubscribeToHeartbeat()`), the settings engine, and time services.

### fr_app

| Folder | Role |
| --- | --- |
| `Device/` | Peripheral drivers owned by this board: `Acc`, `Flash`, `Gps`, `LoraRadio`, `MicroSD`, `Farmranger` (UART link to the fr9 board). Bus I/O via `Hal/`, plus device protocol and health/retry logic. |
| `Worker/` | Subsystems with their own lifecycle or state machine: `Battery`, `Fota`, `FrKernel`, `MeshNetwork`, `Movement`, `Power`, `SolarPower`. Built on one or more Devices. |
| `Tasks/` | Outermost application behaviour: `DeviceDiscovery` (the main AppTask — primary/secondary campaign loop, radio scheduling, drives Fota and MeshNetwork sessions) and `RadioTest` (bench mode). |
| `inc/`, `src/` | Cross-cutting glue that is not a module: `main.c`, `init.c` (boot sequencer), `DbgLog`, `flashLog`, `math_func`, `time_driver`, `uart_callbacks`, `inc/config/` build and version headers. |
| `settings/` | `settings_default.c/h` — the persisted-settings struct and its compile-time defaults. |

Per-module file pattern:

- `<Module>.h` — public API.
- `<Module>.c` — implementation.
- `<Module>_Config.h` — compile-time constants: register layouts, timings, retry counts, part
  numbers. Non-obvious values carry a rationale comment.
- `<Module>_Driver.h` — thin macro layer mapping `MODULE_DRIVER_xxx()` onto the underlying
  `Hal` call, so the module does not name a bus API directly. Present where a module touches
  hardware (Flash, GPS, Battery, Movement); absent where a module only orchestrates others
  (Power, FrKernel, MeshNetwork).

## Concurrency model

There is no task registry. `fr_app/src/init.c` is a single ordered bootstrap that calls each
subsystem's `MODULE_vInit()` in a documented sequence, then exits its own thread. Each module
wires itself up inside its own init.

Two idioms:

1. **Heartbeat only** — the module subscribes to Platform's 1 Hz heartbeat and does its work
   on the dispatch task; no thread of its own.
2. **Own thread** — `_vInit()` calls `osThreadNew()` with a static `osThreadAttr_t`, and the
   thread body subscribes to the heartbeat before entering its loop (see `Power.c`, which
   only spawns `PowerStateMgr` on secondary devices).

## Naming conventions

Functions are `MODULE_<returnTypeCode><VerbNoun>`:

| Code | Return | Example |
| --- | --- | --- |
| `v` | void | `FLASH_vInit()` |
| `b` | bool | `FLASH_bDevicePresent()` |
| `u8`/`u16`/`u32` | fixed-width unsigned | `VERSION_u32Get()`, `FLASH_u16GetAndClearReadFails()` |
| `t` | struct/handle type | `PLATFORM_tGetHeartbeatDispatchTaskHandle()` |
| `e` | enum | `DEVICE_DISCOVERY_eGetDeviceRole()` |

Types are `PascalCase_t` (`Flash_Health_t`, `FwVersion_t`). Constants are
`MODULE_SCREAMING_SNAKE`. Header guards mirror the physical path
(`DEVICE_FLASH_FLASH_H_`, `TASKS_DEVICEDISCOVERY_DEVICEDISCOVERY_H_`).

## Logging

`fr_app/inc/DbgLog.h` is canonical (`dbg_log.h` is a forwarding shim for older includes).
All macros format into one RAM ring buffer drained by a background consumer task, so
producers never block on UART or flash:

- `DBG()` — debug UART only. `LOG()` — external-flash text log only. `DBG_LOG()` — both.
  These are verbose: each line is prefixed with date/time and battery voltage.
- `_DBG_()`, `_LOG_()`, `_DBG_LOG_()` — plain, no prefix. Use where the message already
  carries its own context.

## Versioning and build

Version lives in `fr_app/inc/config/version_config.h` (`VERSION_SW_MAJOR/MINOR/PATCH`,
currently 3.1.1). Bump policy follows the Farmranger coding standard section 12 — that
document is external to this repo, so ask rather than infer version policy from the code.

`version_config.c` places a `const FwVersion_t gFwVersion` in the linker's `.fw_info`
section at app base + `0x200`, so any reader (bootloader, build script, fr9) can learn an
image's true version from the bytes themselves rather than from a filename or manifest.

`build_scripts/create_release_hex_files.ps1` runs after every CubeIDE build and:

1. Reads MAJOR/MINOR/PATCH out of `version_config.h` by regex — keep those macro names and
   this file path in sync with the script.
2. Emits `frtag3_<M>_<m>_<p>.hex` and, when a bootloader build exists, a combined
   `frtag3_<M>_<m>_<p>_bl_<b>.hex`.
3. Verifies the built `.bin`'s embedded `.fw_info` matches `version_config.h` and aborts on
   mismatch. This gate exists because on 2026-09-01 three releases produced identical size
   and xor8, and an old image was served under a new version number.
4. Publishes the app-only `.bin` plus `version.json` into
   `C:\Code\farmranger-firmware\frtag3-firmware` and
   `C:\Code\frtag-firmware-inhouse\frtag3-firmware`. It writes files only — it never commits
   or pushes those repos.

frtag3 has no bootloader project of its own yet, so the script still reads the bootloader hex
from `../frtag2_bootloader`.

## OTA

`fr_app/Worker/Fota/Fota_Config.h` is a byte-identical mirror of the same file in
`frtag2_bootloader/fr_bootloader/inc/` — it is the app/bootloader contract, so any change
must be made in both places. This coupling still points at frtag2's bootloader and will need
resolving when frtag3 diverges.

Flow: fr9 fetches `version.json` and the `.bin`, streams it over UART to the primary tag; the
primary writes it into the external NOR scratchpad (mapped 1:1 to the app base address),
validated by a streamed 8-bit XOR plus a `"FROT"` metadata record, then re-checks the image's
own `.fw_info` before accepting it. The primary LoRa-distributes the staged image to
secondaries in windowed chunk sessions with a repair pass; secondaries only accept while
explicitly armed. On success either side writes `TAMP->BKP0R = OTA_BOOT_MAGIC` and the
version to `BKP1R`, then resets; the bootloader compares against the installed app's
`.fw_info` read straight from flash and programs only if strictly newer.

## Build configuration

`fr_app/inc/config/build_config.h` is the single point of control for what gets compiled into
an image. Reading that one file must give the complete picture of the build — feature
toggles, log and debug verbosity levels, the FrKernel command interface transport, the
storage backend, the debug transport, and anything else that varies between images.

Rules:

- A new compile-time option goes in `build_config.h`, never into an IDE preprocessor symbol,
  a scattered `#define` in a module header, or a `_Config.h`. The per-module `_Config.h`
  files hold tuning constants for a module that is being built; they do not decide *whether*
  or *in which shape* it is built.
- Mutually exclusive or mandatory selections get an `#error` guard in the "Compile-time
  guards" block at the bottom of the file, so a bad combination fails the build instead of
  producing a silently wrong image.
- Each option carries a comment saying what it does and pointing at the module that consumes
  it.
- `INIT_vInitialization()` logs the active option set over `DBG_LOG` at boot, so "what is
  actually on this board" stays recoverable from the terminal or the persisted log. Any
  option added to `build_config.h` should be added to that banner too.
- The only exceptions are toolchain plumbing symbols (`DEBUG`, `CORE_CM4`, `USE_HAL_DRIVER`,
  `STM32WLE5xx`, `USE_FULL_LL_DRIVER`), which must stay project preprocessor symbols because
  CMSIS/HAL sources compile before any of our headers are visible.

Watch for comment placement: a trailing multi-line block comment after a `#define` stops
being a comment the moment the define is commented out with `//`, and its tail lands in the
translation unit. Put explanatory notes above the line.

## Settings

`Platform/inc/settings.h` is an offset-based accessor engine over the `Settings_EE` struct in
`fr_app/settings/settings_default.h`. Callers never touch struct fields — they use
`SETTINGS_u32GetWord(field)` style macros that resolve to `offsetof()` and dispatch to
`SETTINGS_*AtOffset()`, so the backing store can change without touching call sites. Every
field has a paired `has_<field>` bool so validation can distinguish "explicitly set" from
"defaulted". `settings_default.c` supplies the seed values used on first boot or after a
failed integrity check.

## House style

- Every file opens with a comment block naming the file and explaining its purpose. The prose
  is deliberately long where the *why* is not obvious, and often records the field incident
  that motivated a constant or a guard. Match that when touching these files — brevity is not
  the goal, explaining non-obvious constraints is.
- Recurring fail-safe idiom: a monotonic gate that only a success can reopen, never closed by
  a single transient (`FLASH_bDevicePresent` / `FLASH_bRecoverDevice`), and failure tallies in
  a counter rather than a log line per occurrence on hot paths
  (`FLASH_u16GetAndClearReadFails`).
